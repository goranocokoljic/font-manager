# The webview against the memory and scroll targets (E35.1)

Measured 2026-10-29 on Windows with `scripts/bench/webview.mjs` (this branch,
base `2b3ecec`), release build (`pnpm tauri build --no-bundle`), the reference
library as the one source, every optional feature on (MCP, previews, watcher).
The script starts the app in a scratch home, attaches to the webview over the
DevTools protocol, waits for the list, idles 60 s, samples memory, scrolls each
list view at three paces for 5 s each, samples memory after each view and after
a last 60 s idle. The raw reports are `target/bench/webview-windows*.json`
(not committed; rerun the script to make them).

**Machine.** AMD Ryzen 9 3900X (12 cores), 64 GB, NVIDIA GeForce GTX 960,
2560×1440 at 60 Hz, Windows 11 Pro 10.0.26300, WebView2 156.0.4314.50.

**Library.** `D:\private\fm-reference-library`: 15,329 faces in 2,544
families (the spec's targets are for 10,000).

**Core alone, same machine** (`scripts/bench.sh`, the `fm-bench` binary, no
webview): cold start 680 ms, first scan 4.9 s for 15,329 files (3.2 s scaled to
10,000), search 27 ms, 100-face activation 28 ms, idle memory 16 MB. Every core
budget holds.

## Verdicts

| Spec target | Result | Verdict |
|-------------|--------|---------|
| Idle memory with 10k fonts < 350 MB (webview UI) | Warm start, 60 s idle: **190 MB** (app 61, webview 129). After the first scan, 60 s idle: **418 MB** (app 276, webview 142); the app process does not give the scan's memory back until restart | Met on a warm start; missed right after a scan |
| Memory after use | After scrolling through every view once: **2.1 GB**; after another 60 s idle: **1.7 GB**, of which the webview renderer holds 1.6 GB | No target in the spec; far above anything a 350 MB idle target intends |
| Scroll at 60 fps in every view mode | Wheel pace (one notch every 50 ms): 60 fps in List, Table, Grid; Waterfall 1 % of frames over 18 ms with a 100 ms frame | Met at reading pace, except a hitch in Waterfall |
| No jank on cache misses | Fling (two notches per frame) and drag (the whole list in 5 s): long frames in every view; List and Grid worst (p95 100–117 ms, up to 38 frames over 50 ms in 5 s) | Missed |
| Cold start to usable window < 1 s | Window with the sidebar in **1.1–1.3 s** from process start; the font list follows at 3.1–3.4 s on a warm index (the list waits for the first page of families) | Just missed for the window; the list is 2 s later |

## Where the cost sits

1. **Font bytes stay in the renderer.** Each row loads its face through
   `font:` URLs as a `FontFace`; `src/preview/faceLoader.ts` drops a face from
   `document.fonts` once more than 48 released faces pile up, and the page
   indeed holds 48–65 faces at any time. The renderer's private memory still
   grows by about 100 KB per face scrolled past and does not come back after
   60 s idle: 1.6 GB after 15,329 faces, which is the size of the library's
   files. The `font:` answers carry `Cache-Control: no-cache`
   (`apps/desktop/src-tauri/src/lib.rs`, `font_ok`), which lets Chromium keep
   the bytes in its in-memory resource cache after the `FontFace` is gone; the
   experiment below rules that out, so the bytes sit in Blink's font cache
   (the decoded font data behind a `FontFace` that nothing on the page
   references any more, which the JS garbage collector is in no hurry to
   release because the bytes are not on its heap).
2. **The Grid view fills the JS heap.** Scrolling the grid once leaves 776 MB
   in the V8 heap (39 MB after the list) and the heap never shrinks again.
   `src/stores/thumbnails.ts` keeps every thumbnail it ever rendered as an
   object URL in a map with no size limit ("until the library changes"), and
   the bytes come over Tauri's IPC as JSON arrays. Which of the two holds the
   heap needs a heap snapshot; both are in the frontend, not in the webview
   itself. The grid cards also rendered blank in this build (the user's
   "Grid doesn't show anything" note).
3. **The app process keeps the scan's memory.** 276 MB after the first scan
   against 61 MB on a warm start and 16 MB for the core alone. The scan's
   working memory is not returned to the OS (allocator retention or a cache
   that is never trimmed); it is a Rust-side fix, not a webview question.
4. **Fast scrolling blocks the main thread.** At fling and drag pace every
   view misses frames. List is the worst: p95 100–117 ms, that is, each new
   window of rows costs 6–7 frames to lay out (a row renders its own face;
   the font has to arrive, be parsed and shaped before the row can paint).
   Table (plain text, no face per row) is close to clean at fling pace; the
   waterfall, which renders a paragraph per row at several sizes, is the most
   expensive per row. At wheel pace the virtualized list keeps up.

## Experiment: `Cache-Control: no-store` on the `font:` scheme

The same warm run with `font_ok` answering `Cache-Control: no-store` instead
of `no-cache` (change reverted, not shipped):

| Sample | Total | App | Webview |
|--------|------:|----:|--------:|
| Idle, 60 s after start | 192 | 62 | 130 |
| After scrolling List | 775 | 80 | 695 |
| After scrolling all four views | 2,488 | 71 | 2,417 |
| Idle again, 60 s | 1,734 | 62 | 1,673 |

No change: the renderer keeps the font bytes whatever the cache header says.
A fix has to make the renderer drop the font data of released faces (for
example a `FontFace` made from an `ArrayBuffer` the loader can let go of, or
fewer, smaller faces on screen), or the list has to leave the webview. That
is E35.3's call; the measurement only shows the size of the problem.

## What E35.2 and E35.3 should take from this

- The webview holds the idle target on a warm start with a 150 MB margin,
  and the core holds every budget of its own. The spec's reason to revisit a
  native shell ("cannot hold 60 fps on 10k-row lists, or the memory target is
  missed") is met on the first count only for fast scrolling, and on the
  second only after use, not at idle.
- Three of the four costs are in the app's own code, not in the webview as a
  platform: the scan's retained memory (Rust), the thumbnail map and IPC byte
  arrays (frontend), and a row design that loads one face per row and lays
  out a paragraph per row in the waterfall. Each can be measured again with
  this script after a fix.
- The one cost that is the webview's own is the retained font data of faces
  the page no longer shows, about 100 KB per face scrolled past. A native
  list would not have it, because it would rasterize through the core. The
  prototype of E35.2 is worth building only if that cost cannot be brought
  down inside the webview.
