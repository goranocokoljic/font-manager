# Grid thumbnails as IPC bytes (E35.5)

Measured 2026-10-30 on Windows with `scripts/bench/webview.mjs` (branch
`E35.5-preview-bytes-ipc`, base `8add192`), release build
(`pnpm tauri build --no-bundle`), same machine and library as
[webview-2026-10-29.md](webview-2026-10-29.md): Ryzen 9 3900X, 64 GB,
2560×1440 at 60 Hz, `D:\private\fm-reference-library` (15,329 faces in 2,544
families). Warm start, default settings of the script (60 s settle, 5 s per
scroll run). No forced garbage collection anywhere in the run. The raw
reports are `target/bench/webview-windows-e35.5-run{1,2,3}.json` (not
committed).

## What changed

1. `render_preview` answers with Tauri's raw IPC response: an 8-byte header
   (width, height: little-endian u32) and the PNG
   (`apps/desktop/src-tauri/src/lib.rs`, `preview_bytes`).
   `src/api/preview.ts` turns it into `{ width, height, png }` with the PNG as
   a `Uint8Array` view, not a number array. fm-api's `PreviewImage`, the local
   endpoint and MCP are unchanged.
2. The content security policy gains
   `connect-src 'self' ipc: http://ipc.localhost`. Tauri's IPC is a `fetch` to
   that scheme; without `connect-src` the policy fell back to
   `default-src 'self'`, blocked it, and **every** command of the app went over
   the message-channel fallback. That channel hands each answer to the page as
   script text, `runCallback(id, JSON.parse('[0,32,0,0,135,…,137,80,78,71,…]'))`:
   a heap sampling profile of one Grid run put 310 MB under `(V8 API)` and
   190 MB under `(PARSER)` for these scripts. With only change 1 (run 1 below)
   the raw bytes still went that way and the heap after Grid stayed at 819 MB.

command now uses the fast channel too.
